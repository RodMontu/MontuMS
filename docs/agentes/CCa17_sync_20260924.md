## Qué se implementó

1. **`backend/routers/sync.py` (nuevo)** — `POST /api/sync/ejecutar` y `GET /api/sync/estado`.
   - `ejecutar_sync(sucursales=None)`: por cada sucursal (1, 10, 14 por defecto), en orden **(a) universo → (b) Cuadro**:
     - (a) `_verificar_cubigest_vivo`: `SELECT TOP 1 it.Id FROM IT ... WHERE IdSucursal IN (...)` vía `cubigest_db.connect()` directo (no `execute_query`, porque esa función traga excepciones y devuelve `[]` — no serviría para distinguir "Cubigest caído" de "sin filas"). Esto es intencionalmente **no un caché nuevo**: el universo sigue siendo consulta en vivo en cada endpoint existente (`_obtener_pids_pendientes`, etc.); aquí solo se valida y registra si el ERP responde.
     - (b) `_sync_cuadro`: llama directamente `scrape_cuadro_programacion(nombre, desde, hasta)` (import directo desde `scraper_cuadroprogramacion.py`, **sin** salto HTTP a sí mismo) para la semana actual (lunes-sábado, mismo criterio que el `__main__` del scraper — TO no despacha domingo). Mapeo sucursal_id→nombre Cubigest: `{1: CALAMA, 10: SANTIAGO, 14: CORONEL}`.
     - Si (b) falla, **no se pisa nada**: `scrape_cuadro_programacion` ya hace el `DELETE`/`INSERT` *después* del parseo completo (confirmado leyendo `scraper_cuadroprogramacion.py:220-257`), así que una excepción de parseo (ej. el 500 de SANTIAGO documentado en A13) deja el Cuadro anterior intacto — solo se registra el error.
     - Nunca reporta `ok: true` global si alguna fuente falló (`ok_global = all(...)`).
   - Tabla nueva `sync_estado(fuente, sucursal_id, ultimo_ok_ts, ultimo_error_ts, ultimo_error_msg, duracion_ms)`, `CREATE TABLE IF NOT EXISTS` ejecutado perezosamente en el propio router (primer uso), sin migraciones. `ultimo_ok_ts` **no se pisa** en un fallo (el `UPSERT` de error solo toca columnas de error) — así el badge puede seguir mostrando "hace Xh" desde el último éxito real aunque la corrida más reciente haya fallado.
   - `GET /api/sync/estado`: por fuente×sucursal, `minutos_desde_ok`, `desactualizado` (umbral `SYNC_DESACTUALIZADO_MIN`, default 90 min, sin ultimo_ok_ts = desactualizado), y `sincronizando` (estado del lock).
   - **Lock único** (`asyncio.Lock` a nivel de módulo): una segunda llamada mientras hay una en curso devuelve `409` con `RuntimeError("Ya hay una sincronización en curso")`. Compartido entre el botón y el job horario.
   - Timeouts: 10s por chequeo de universo, 60s por scrape del Cuadro (`asyncio.wait_for`), para que el botón nunca cuelgue la UI indefinidamente.
   - Validación de `sucursal_id` (400 si no es 1/10/14) antes de tocar el lock.

2. **`backend/main.py` (modificado, ~26 líneas)** — import de `sync` en la lista de routers, `app.include_router(sync.router)`, y el job horario:
   - Registrado **solo si `SYNC_HORARIO_ACTIVO=1`** (default `0`/apagado — con el flag apagado el job ni se agrega al scheduler, tal como pide el encargo).
   - Cron por defecto: minuto 5, lunes a sábado, 06:00-22:00 America/Santiago (`CronTrigger(day_of_week="mon-sat", hour="6-22", minute=5, ...)`), overrideable con `SYNC_HORARIO_CRON` (formato crontab de 5 campos, vía `CronTrigger.from_crontab`).
   - El job llama la misma `ejecutar_sync()` que usa el botón — si el lock está tomado (ej. alguien apretó "Sincronizar" a la misma hora), el job lo loguea como omitido en vez de fallar.
   - **Cómo encenderlo:** `SYNC_HORARIO_ACTIVO=1` en el `.env` del backend (y `docker compose up -d --force-recreate` para que tome la env var — no `restart`, per protocolo Docker). Montu decide cuándo, porque golpea Cubigest y el scraper OptiSteel cada hora en horario laboral.

3. **`frontend/src/components/domain/SyncEstado.tsx` (nuevo)** — componente aislado, no integrado en `GestorProgramacion.tsx` porque ese archivo está bloqueado (rama `b42v2-etiqueta`). Botón "Sincronizar" (llama `POST /api/sync/ejecutar` con `sucursal_id`) + badges por fuente (Universo/Cuadro, verde si al día, ámbar con ícono de alerta si `desactualizado`, tooltip con el último error) + polling de `GET /api/sync/estado` cada 60s.

## Pruebas

`backend/test_sync_unificado.py` (unittest, mismo estilo que `test_b16_capacidad.py`), 7 casos, todos con mocks de `scrape_cuadro_programacion` y `_verificar_cubigest_vivo` (nunca toca Cubigest/Cubigest real ni el scraper real):
- Éxito total en las 3 sucursales × 2 fuentes.
- Fallo del Cuadro → `ultimo_ok_ts` previo se conserva intacto, error queda registrado, universo no se ve afectado.
- Fallo del universo (Cubigest "caído") → no bloquea que se siga intentando el Cuadro, error registrado sin tocar `ultimo_ok_ts`.
- Lock concurrente → de dos llamadas simultáneas (`asyncio.gather`), una gana el lock y la otra recibe `RuntimeError`.
- `desactualizado` por umbral: sin corridas = desactualizado; `ultimo_ok_ts` de hace 200 min (umbral 90) = desactualizado; de hace 5 min = no desactualizado.
- `sucursal_id` inválido → `ValueError`.
- Flag de job apagado por default (chequeo directo de la env var, sin levantar el lifespan completo — requeriría Cubigest/SQLite reales).

## Decisiones y riesgos

- **No toqué `_obtener_pids_pendientes` ni el `except Exception: return []`** que documenta CCa-11 (§4 riesgo 4, plan #3) — está fuera del alcance de esta tarea (pasos 1/2/5) y cambia el contrato de una función con 3-4 callers; queda pendiente para cuando se aborde el punto #3 del plan.
- **No usé `POST /api/admin/cuadro-programacion/ejecutar` vía HTTP** para disparar el scraper — llamé `scrape_cuadro_programacion` directo (mismo proceso). Es más simple y evita un salto de red innecesario a sí mismo; el endpoint HTTP existente sigue intacto para el disparo externo de Geovictoria.
- **Rango de fechas del Cuadro fijo a la semana actual (lunes-sábado)** — igual al `__main__` del propio scraper. Si Montu quiere que la sync horaria cubra más rango (ej. próxima semana también), es un cambio de una línea en `_rango_semana_actual()`.
- **Riesgo del job horario**: aunque está apagado por default, una vez encendido corre en horario laboral (06:00-22:00) contra el ERP de producción del cliente — confirmar con Montu la cadencia real antes de poner `SYNC_HORARIO_ACTIVO=1` en el `.env` de producción.
- **No se implementaron los puntos #3, #4 y #6** del plan CCa-11 (blindar `_obtener_pids_pendientes`, refactor del scheduler a `_obtener_pids_pendientes_optisteel`, unificar ventana `-30d/+21d` con "muy futura") — explícitamente fuera del alcance de este encargo (solo pasos 1, 2 y 5).
