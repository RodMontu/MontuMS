## Paso 3 — ¿Por qué no sale ni "32 x 0"? (detalle)

No hay piezas con diámetro 0 ni largo 0/NULL en `Piezas` de Cerrillos en 60 días (0 filas en `Largo IS NULL OR Largo <= 0 OR Diametro <= 0` sobre 7.369 filas). La "x 0" no viene de `Piezas`, sino del **decodificador de códigos** (ver Paso 4). El balance de stock sale de `EtiquetaAZA` (`obtener_stock_bodega`, `database_cubigest.py:104`), no de `EstExi1`.

## Paso 4 — "32 x 0 mm": causa y alcance

**Causa (verificada en código y en la API):**
`backend/utils.py` `decodificar_material`:
- `:71` `diametro = int(codigo[5:7])`
- `:76` `largo = int(codigo[8:10])` — asume largo entero de 2 dígitos tras la `X`
- `:82` `descripcion += f" x {largo}m"`

Códigos con largo **decimal de dígito simple** (`X6,9`, `X6.9`, `X9,9`) → `codigo[8:10]` = `'6.'` / `'9,'` → `int()` falla → `largo = 0` → **"32mm x 0m"**. Los decimales de 2 dígitos (`X10,8`, `X11,9`) sí se leen (10/11 m).

**Inconsistencia de codificación en la fuente (Cubigest):** el mismo largo físico aparece con separador distinto:
- `EtiquetaAZA` (Cerrillos, Id_Sucursal 4): `1B63N32X6.9`, `1B63T32X6.9` (punto) y `1B63T25X9,9`, `1B63N28X7,3` (coma) — 11 códigos distintos con decimal, 245.593 kg en etiquetas históricas (5 con coma: 243.857 kg; 6 con punto: ~1.736 kg).
- `EstExi1` (BodCod 1, año 2026): 9 códigos con decimal (siempre coma), 9.675 kg: `1B63T25X9,9` (5.499), `1B63T32X6,9` (2.745), `1B63N36X8,6` (481), `1B63N32X6,9` (436), `1B63N36X6,5` (260), `1B63N36X5,3` (254) + 3 con saldo 0.

**Presencia real en el balance (API, sucursal 10):** exactamente 2 materiales mal decodificados con saldo > 0:
- `1B63T32X6.9` → "Barra A630 32mm **x 0m**" → 305 kg ← **el "32 x 0 mm" de la minuta**
- `1B63T25X9,9` → "Barra A630 25mm **x 0m**" → 611 kg

Total mal decodificado visible hoy: **916 kg** (el resto de códigos con decimal está totalmente consumido/vinculado y no sale en el balance).

**Relación con el paso 3 (IT 339):** **Ninguna directa.** "32 x 0 mm" es un bug de decodificación de stock por código de etiqueta; IT 339 no aparece por la ventana de fechas y por ausencia de piezas. Son dos problemas independientes que la misma minuta mezcla.

## Propuesta

1. **Responde a la minuta (sin código):** el ~12 t de IT 339 (D3, PEN, 10.772 kg) no aparece porque su despacho está planificado para 2026-12-26 (fuera de la ventana +21d) y porque en Cubigest no hay piezas registradas para ese IT (ni para D2). El balance usa `Piezas`, no `IT.TotalKgs`. "32 x 0 mm" es otro bug, de decodificación de código (6,9 m leído como 0 m).
2. **Fix de `decodificar_material` (`backend/utils.py:76`):** parsear el largo aceptando separador decimal: tomar `codigo[8:]`, normalizar `','`→`'.'`, y si hay `.`/`,`, leerlo como float (máx. 2 decimales); si el parseo falla, marcar el código como inválido en lugar de silenciar a 0 (p. ej. `"largo_mm": null` + descripción "largo inválido").
3. **Normalizar en la fuente:** validar en la carga de etiquetas Cubigest el formato de largo (`X` + 2 dígitos, o `X` + d.d con separador único) y unificar el separador decimal (hoy conviven punto y coma para el mismo largo).
4. **Opcional (decisión de producto, no fix):** vista secundaria "demanda fuera de ventana" o fallback a `IT.TotalKgs` cuando el IT válido no tiene piezas, para que la demanda futura visible no dependa 100% de que `Piezas` esté cargado.
